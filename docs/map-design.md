# 地图设计研究

> 这份文档记录"地图"这件事的研究结论：地图长什么样、金币和加速带摆哪、
> 子弹时间和断崖怎么配合、地图还能跟玩家玩出什么交互。
>
> 结论都带具体数字，数字来自 `src/world/maps.js` 和 `src/world/track.js` 的真实几何
> （用 `CatmullRomCurve3` 按弧长采样后算出来的），不是估的。

---

## 0. 现状盘点

现在有两条赛道，都定义在 `src/world/maps.js`：

| 地图 | 长度 | 路宽 | 形状 | 特殊结构 |
| --- | --- | --- | --- | --- |
| 晴日草原 `grassland` | 991 m | 20 m | 330 点闭合样条：直道 + 高速弯 + 一个 R=24 发夹弯 | 无 |
| 熔岩环道 `volcano` | 1273.7 m | 18 m | 长直道 + 发夹弯 + S 弯 | 一座 197 m 的高架断桥 |

地图这一层目前只回答了"路怎么走"，没有回答"这张图上有什么可玩的"。
逐个方向的研究结论在下面。

## 1. 地图设计

### 1.1 现状

`maps.js` 里一张地图 = 控制点 + 路宽 + 主题配色 + 曲子 + 断桥参数。
配色和地形是分开的两套（`theme.scenery` 决定用 `meadow` 还是 `volcano` 那套场景生成器），
这个分层是对的，不用动。

### 1.2 结论

**地图应该拆成两层：几何层（不可变）+ 玩法层（每张图自己写）。**

现在几何（控制点、路宽、断桥）和玩法（道具摆法）混在两张地图条目里，
真正的问题是**道具摆法是全局的**（`PROPS.boostPadParams` 一个数组管所有地图），
而道具摆法恰恰是最"每张图各有道理"的东西。

本轮已经把摆法下沉到地图自己身上：

```js
props: {
  coins: { runs: [{ t: 0.05, offset: -3 }, ...], count: 4, spacing: 7 },
  boosts: [{ t: 0.09, offset: 0 }, ...],
}
```

### 1.3 还没做的（下一步）

- **路宽随位置变化**：现在一张图只有一个 `width`。真实赛道有"发夹弯收窄、直道放宽"，
  用 `widthAt(t)` 就能做，比多切几张图便宜得多。
- **坡度剖面**：`track.heightAt(t)` 现在只服务断桥一张图。
  如果把它做成通用的"这张图的海拔剖面"，就能做上坡、下坡、连续起伏。
- **地图元数据**：圈数、难度、是否有断桥、是否适合新手，应该写进地图条目，
  让 UI 能显示"这张图有断桥，新手慎入"。

## 2. 子弹时间

### 2.1 现状

`config.js` 的 `TIME`：

```js
slowMoScale: 0.3,   // 腾空时世界慢到 30%
slowMoLerp: 6,      // 倍率切换的快慢
recoverDelay: 0.15,
```

触发条件在 `game.js`：**车腾空且不在坠落**（`car.airborne && !falling`）。
也就是说子弹时间目前是"断桥飞跃的专属演出"，不是玩家的能力。

### 2.2 三个问题

1. **玩家不能主动用。** 没有键位、没有资源、不能用在小场面里。
   现在的它更像"过场动画开关"，而不是玩法。
2. **没有"世界慢、玩家不慢"的分层。** `timeScale` 直接乘在整帧 dt 上，
   物理、动画、计时一起慢。这在飞跃演出里是对的（画面连贯），
   但如果要让玩家用它来救场，就得让**车保持满响应、只有世界变慢**，
   否则按键会变得像"半速操作"，非常难受。
3. **没有任何视听反馈。** 没有低通滤波、没有变暗、没有画面边缘收缩，
   玩家只能靠"车飘得慢"这件事自己察觉。

### 2.3 结论：拆成两种子弹时间

| | 演出型（现有） | 能力型（待做） |
| --- | --- | --- |
| 触发 | 自动（腾空） | 玩家按键 `Q` + 有资源 |
| 慢谁 | 全世界（含车） | 只有世界，车保持满速 |
| 用途 | 让飞跃更有分量 | 窄弯救车、贴着断口过、极限微操 |
| 反馈 | 慢动作 + 特写镜头 | 额外要有：低通音、边缘收缩、暗角 |

能力型需要三样东西：

- **充能资源**：比如每圈给 1 次，或者靠漂移攒（和氮气同一套资源但分开一条）。
- **世界慢放要分层**：物理给车的是 `dt`，给道具/粒子/幽灵车/环境的是 `dt * timeScale`。
  现在 `game.js` 里 `step` 一个值走天下，要拆成两个。
- **音频**：慢放时给引擎音和音乐加一个低通滤波器，`timeScale` 直接映射到 `filter.frequency`，
  这是最便宜也最有效的"时间变慢了"信号。

### 2.4 顺带发现的另一个问题

`config.js` 里的 `TIME.recoverDelay` **根本没被用过** —— `game.js` 里没有任何地方读它。
要么用起来（落地后延迟 0.15 秒才恢复速度，让落地更有分量），要么删掉。

## 3. 断崖

### 3.1 现状

只有"断桥"一种：`track.heightAt(t)` 在桥区间返回桥面高度，在断口区间返回 `null`，
路面生成时遇到 `null` 就不生成三角形 —— 那里真的没有桥板。

车掉下去靠 `CAR.fallLimit = -2` 判定，触发 `#respawnAfterFall()` 拉回上一个站稳点。

### 3.2 桥面是怎么生成的

桥面不是一个独立物体，是"一条高度剖面 + 一条三角带"叠出来的，分三层。

**第一层：5 个数 → 一条海拔曲线**（`maps.js` → `track.heightAt`）

```js
bridge: { from: 0.020, to: 0.175, gapFrom: 0.108, gapTo: 0.123, height: 6.5 }
```

| 区间 | `heightAt(t)` 返回 |
| --- | --- |
| `t < from` / `t > to` | `0`（地面） |
| `from → gapFrom` | `smoothstep(p) × height`，p 是区间内进度 |
| 其中最后 3% | 再叠 `k² × 3.4` 的起跳唇，k 是唇内进度 |
| `gapFrom → gapTo` | `null`（没有地面） |
| `gapTo → to` | `height × (1 − smoothstep(p))` |

**第二层：曲线采样 → 抬高路面**（`track.#buildRoad`）

1200 个按弧长均匀的采样点，每点取一次 `heightAt(i / N)`，把路面三角带的左右顶点抬到
`surfaceY + h`。断口处返回 `null`，这一段干脆不生成三角形 —— 断口是真的缺一块，
不是把桥面涂成熔岩色。

**第三层：补"桥"的结构**（`track.#buildBridge`）

腹板 1.8 m、护栏 1.5 m + 立柱、桥墩 + 盖梁、警戒条、发光条、碎板。
这些全是外观，不参与碰撞：**车能不能站住只看第二层的 `heightAt`。**

所以：改桥的形状 = 改 `heightAt`；改桥的样子 = 改 `#buildBridge`。

熔岩环道的实测数据（`node tools/bridge-deck.mjs`，真实曲线 1273.7 m / 1200 采样）：

```
桥面全长   197.4 m       断口 19.1 m（物理）/ 20.2 m（视觉，采样量化差 1.1 m）
上桥坡道   112.1 m       起跳唇 38.2 m，最高 9.79 m
落地坡     66.2 m        断面 21.4 m 宽（18 路宽 + 1.7 路肩 ×2）
结构       12 根桥墩 / 6 根盖梁 / 28 根护栏立柱 / 10 块碎板
```

（本节旧版写的是 446 m / 桥高 7.5 m / 唇高 10.81 m —— 那是桥还架在
`t=0.02~0.42` 时的数据；桥挪到起跑直道后全部作废，以本节为准。）

### 3.3 实测：真正的门槛不是 34 m/s

把 `car.#updateVertical` 和 `game.js` 的取点方式（每帧前进 → 最近采样点 → `surfaceAt`）
逐行复刻后仿真（60 fps，恒定水平速度，`tools/bridge-deck.mjs`）：

| 速度 | 滞空 | 飞行最低点 | 相对桥面（6.50 m） | 结果 |
| --- | --- | --- | --- | --- |
| 20 m/s | 0.883 s | −2.18 m | — | 掉进熔岩 |
| 22 m/s | 0.867 s | −1.56 m | 低 8.1 m | **过**（被吸上来） |
| 25 m/s | 0.767 s | 1.26 m | 低 5.2 m | 过（被吸上来） |
| 30 m/s | 0.633 s | 4.46 m | 低 2.0 m | 过（被吸上来 2 m） |
| 34 m/s | 0.567 s | 5.86 m | 低 0.6 m | 过 |
| 55 m/s（极速） | 0.350 s | 9.29 m | 高 2.8 m | 过 |
| 82.5 m/s（氮气） | 0.233 s | 9.90 m | 高 3.4 m | 过 |

**门槛 ≈ 21.9 m/s（极速的 40%），而且"过不过"由 `CAR.fallLimit = −2`
（掉进熔岩的判定线）决定，不是由断口宽度决定。** 原因是两个独立的问题：

1. **起跳斜率被砍半。** `surfaceAt` 在断口前一格算差分时，前向采样是 `null`，
   代码用 `y` 顶替，于是 `(y − before) / (2·eps·L)` 只算到真实坡度的一半：
   唇口几何 9.8°，游戏只给 5.0°。车起跳的竖直速度因此只有应有的一半。
2. **落地判定会把人从桥面底下吸上来。** `#updateVertical` 只判 `y <= groundY`，
   不要求"从上方穿过桥面"。于是车在断口里掉到 1.26 m，等对面桥面一出现就被
   `y = groundY` 直接吸到 6.50 —— 掉下去 5.2 m 也算过关。

把两处分别修掉后的门槛：

| 改法 | 门槛 |
| --- | --- |
| 当前代码 | 21.9 m/s（40%） |
| 只修起跳坡度 | 20.3 m/s（37%） |
| 只修落地判定 | 36.2 m/s（66%） |
| 两处都修 | 31.0 m/s（56%） |
| `map-check` 的理论值（假定完整唇口坡度） | 30.7 m/s |

结论：`maps.js` 注释里写的"34 m/s / 62%"没有实现；两处都修后是 31 m/s / 56%。
如果一定要保住 34 m/s 的设计意图，断口要从 19.1 m 加宽到约 21.5 m
（两处都修后，34 m/s 的滞空距离就是 21.5 m）。

### 3.4 桥面生成出来的五个缺陷

| 缺陷 | 原因 | 后果 |
| --- | --- | --- |
| 断口没有端面 | 路面是零厚度三角带，`#buildRoad` 遇 `null` 直接跳过，两侧腹板也只是竖片 | 塌口露出的是一条"边"，不是一块板的切口 |
| 腹板 / 护栏有一侧是透明的 | `#buildVerticalRibbon` 返回 DoubleSide，`#buildBridge` 又换成单面的 `toon(...)`；两侧绕序相同 → 一侧朝内、一侧朝外 | 从赛道上看总有一条护栏/腹板看不见 |
| 桥墩顶面与桥面共面 | 桥墩高 = `height + surfaceY`，顶面正好落在桥面上（插值高差 0.0 cm） | 12 处 z-fighting |
| 断口发光条在熔岩底下 | `heightAt(gapFrom)` 是 `null`，`?? 0` 把高度当 0 → y = −0.05 | 两根发光条都沉在熔岩 0.22 m 之下，等于没生成 |
| 中线虚线漏 3 块到原点 | InstancedMesh 里落在断口的实例直接 `return`，矩阵留在单位阵 | 世界原点 (0,0,0) 浮着 3 块虚线 |

桥的"厚度"本身也不是实心的：只有两侧 1.8 m 的裙板，底板就是路面网格的背面。
从侧面看够用，但封口必须靠端面补，不能指望腹板。

### 3.5 怎么生成一块像样的桥面

**方案 A：最小改动（约 25 行，全在 `track.js`）**

1. **断口封口**：在"最后一格地面采样点"和"第一格落地面采样点"各放一个四边形，
   从 `h` 到 `h − 1.8`、宽 `2·edge`。注意别贴在 `gapFrom` / `gapTo` 上 ——
   采样量化让它们和真实桥板边缘差 0.7 m / 0.4 m，封口会悬空。
2. **腹板、护栏材质加 `side: THREE.DoubleSide`**，或者把断面做成闭合的。
3. **桥墩高度改成 `h − 1.8`**，顶面落到腹板底，z-fighting 一起消失。
4. **发光条高度改用 `heightAt(edgeT ± 0.001)`** 取，不要用断口上的 `null`。
5. **中线实例数改成实际生成数**（先数一遍有效 t，再 `new InstancedMesh(..., n)`）。

**方案 B：断面扫掠（约 120 行，推荐给下一张图）**

把桥面写成"一个断面沿曲线扫"：

```
断面（横向 x，竖向 y）：
  ( w,  0) ── 桥面外沿
  ( w, −T) ── 底板
  (−w, −T)
  (−w,  0)
```

- 每个采样点用 `heightAt` 和法线把断面 4 个角摆到世界坐标，相邻两组拼成闭合管；
- 断口处断开，并在两端直接用断面封口 —— 塌口自然有"板厚的切口"；
- 顶面比路面低 2 cm，让路面继续当行驶表面，不打架；
- 护栏单独用 0.35×1.1 的闭合断面扫一遍，双面可见；
- `bridge` 增加 `deck: { thickness, overhang, barrier }`，默认值保持现在的观感。

好处是底板、端面、双面护栏一次解决；以后要加第二座桥、弯桥、连续高架，
只换 `heightAt` 的剖面，不用再写一套几何。

**先做哪个**：A 能立刻消掉"断口是一张纸"和"有一侧护栏是空的"这两个最出戏的问题；
B 是为悬崖图 / 连续高架铺路。建议先 A，等第二座桥真的出现再 B。

### 3.6 一个还没定的设计问题：上坡不减速

**上坡目前不减速。** `car.js` 的 `#updateVertical` 只把坡度换算成竖直速度，
水平速度一点没少 —— 所以爬那 112 m 的上坡是"免费"的，
到了唇口还剩多少速度完全取决于进弯前留了多少。

- **保持街机做法**（现状）：坡不减速，门槛只由断口宽度和唇口高度决定，
  桥的作用是"让你有机会掉速"，而不是"爬桥会掉速"。
- **加上坡度减速**（真实一点）：`vf -= CAR.gravity * slope * dt`。
  代价是玩家必须在上桥前保留速度，桥才真的成为"蓄力→释放"的节奏点；
  但门槛会大幅提高，需要把断口收窄。

现在的实现是第一种。**这个选择会改变整张图的难度曲线，建议先定。**

### 3.7 断崖（区别于断桥）是什么

"断崖"和"断桥"是两种不同的地形：

- **断桥**：路还在，只是中间塌了一段，掉下去 = 掉进熔岩。
- **断崖**：路本身就是窄的、贴着一道悬崖边沿走的；掉下去 = 掉出地图边界。

断崖在当前代码里其实**几乎已经支持**：`heightAt(t)` 只处理一座桥，
但如果把它改成"海拔剖面数组"，就能做出一整段架在悬崖边上的路。
视觉上需要补的是崖壁和崖底（现在只有桥墩和护栏）。

真正缺的是**判定**：现在掉出赛道只是"草地上减速"（`offTrackSpeedFactor`），
而断崖要求"掉出路面 = 直接判负重生"。所以需要给赛道加一个
"致命边缘"的概念（哪一段的两侧是悬崖）。

## 4. 地图交互

### 4.1 现状

地图和玩家的交互只有两处：

1. 断桥：靠近时 HUD 弹一句"前方断桥 · 加速冲过去"（`bridgeWarned` 只弹一次）。
2. 幽灵车 / 最佳成绩按地图分开存。

除此之外，地图对玩法**没有任何影响** —— 换一张图，除了长得不一样、手感完全一样。

### 4.2 结论：地图应该至少改变"节奏"

一个地图如果只是"同样的赛道换个皮"，玩家第二张图就没动力玩了。
建议每张图至少有一项**专属机制**，而且要能用现有的系统表达（不引入新引擎）：

| 想法 | 怎么用现有系统实现 | 成本 |
| --- | --- | --- |
| 断桥（已有） | `track.heightAt` 返回 `null` | 低 |
| 岩浆喷发 | `props` 里加一类"周期性地短暂出现的障碍"，碰了就减速 | 中 |
| 移动路障 | `props` 加一类沿赛道来回移动的障碍 | 中 |
| 旋转闸门 | 同上，只是绕一个轴转 | 中 |
| 捷径 | 赛道分叉：一条近但有风险、一条远但稳 | 高（要改 `nearest` 逻辑） |

前三项都能塞进 `props.js`，只要把 `Coins` / `BoostPads` 抽象成
"按地图数据生成的一组可碰撞道具"。这是最划算的一步。

### 4.3 一个已知的小坑

`bridgeWarned` 原本在 `setMap()` 里才重置，`resetWorld()` 里没有 ——
结果**第一局冲桥会弹提示，第二局开始就再也不弹了**。
本轮已修（挪进 `resetWorld`）。

## 5. 金币和加速带的位置

### 5.1 现状（修之前）

- 金币：每局开始时**随机**撒 10 串 × 3 枚，横向偏移也随机。
- 加速带：全局 5 个固定 t 值（0.16 / 0.34 / 0.52 / 0.7 / 0.86），横向偏移随机。

### 5.2 修之前的三处实际错误（熔岩环道）

断桥让路面分了层，但道具还按"地面是平的"在摆，于是：

1. **加速带 0.34 被埋在桥板下面 1.2 m** —— 玩家看得见路，看不见带子。
2. **加速带 0.52 在离桥面 6.6 m 的半空下方** —— 同上，而且那正好在熔岩河上。
3. **落在桥区间的金币全在桥板底下或悬在断口上方的熔岩里** ——
   断桥占全图 40%，这一段的金币基本吃不到。

（加速带 0.52 离断口只有 0.048 t = 54 m，看着像"过桥后马上给一推"的好设计，
   但它其实埋了 6.6 m —— 这就是为什么必须有工具去核对，不能靠眼看。）

### 5.3 修法

- 金币、加速带的高度一律取 `track.surfaceAt(t).y`，**跟着路面走**。
- 落在断口（`surface.y === null`）上的道具直接不摆。
- 加速带用正交基贴到路面上，桥坡上会跟着倾斜，不会插进桥板。
- 摆法下沉到每张地图自己的 `props` 里（见第 1 节），不再随机。

修完用真实几何核对过：

```
晴日草原  金币 48 枚，悬空偏差最大 0.000 m，落在断口的 0 枚，加速带异常 0 条
熔岩环道  金币 44 枚，悬空偏差最大 0.028 m，落在断口的 0 枚，加速带异常 0 条
```

### 5.4 摆位原则（给以后加地图用）

| 道具 | 摆在哪 | 为什么 |
| --- | --- | --- |
| 加速带 | 出弯之后、进入直道的位置 | 弯中加速只会让你冲出去 |
| 加速带 | 上坡之前 / 起跳唇之前 | 给"需要速度"的地方一个解法 |
| 金币串 | 直道、横向偏一点 | 偏一点才有"绕着走"的乐趣，正中间反而没意思 |
| 金币串 | 桥面上（断口前后） | 高度本身就是风险，回报是金币 |
| 加速带 | **不要**放在断口正上方 | 没有路面，放了也没用 |

### 5.5 还没做的

- **金币没有分数差**：现在吃到就是 +1（`race.addCoin()`），
  可以改成"连续吃到一串有连击倍率"，让"追着一条线吃"变成有收益的玩法。
- **金币不重置位置**：`Coins.reset()` 每局重摆（现在摆法确定了，所以每局一样）。
  如果想让金币"一局只吃一次"，就不该在开局重摆。
- **加速带一次触发后要等 0.4 s**（用 `pad.flash` 判断），高速穿过可能重复触发。

### 6.1 在浏览器里跑出来的另外三个问题

前面的问题靠算几何就能发现，但下面这三个**只有把游戏跑起来、对着画面查才能看见**：

1. **熔岩河把路面埋了。** 熔岩河原本是"沿桥方向摆的一个长方体"。
   赛道是弯的，直盒子会盖到桥以外的路面上去 —— 那段路直接埋进发光的熔岩里，
   车开过去等于开进岩浆（`t≈0.82` 的那条路面和上面的加速带都被埋了）。
   改成顺赛道曲线铺带子、宽度按桥面高度渐变后，熔岩只出现在桥底下。
2. **熔岩裂缝和碎岩块会随机长在赛道上。** 树有"离赛道 22 米"的检查，
   裂缝和岩块却只是随便撒 —— 一条 41 米长的裂缝横在路中间，把加速带盖住了。
3. **加速带和中线虚线共面。** 两者都在 `surfaceY + 0.03`，
   既是 z-fighting，虚线还会从加速带底下穿出来。
   加速带抬到 `surfaceY + 0.07` 就分开了。

修完的核对（浏览器里读真实运行时数据 + 射线遮挡检查）：

```
熔岩环道  金币 44 枚 → 0 枚落在断口、0 枚被遮挡、离地 1.47~1.52 m
          加速带 6 条 → 0 条落在断口、0 条被遮挡、贴路面偏差 0.12 m
          全赛道 120 个采样点 → 0 处路面被熔岩盖住
控制台错误：无
```
